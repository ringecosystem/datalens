# 02 - 系统架构

这一步把项目方向转换成具体系统形态。目标是让每个实现任务都落在正确模块里，而不是把
API 兼容、EVM 细节、查询规划、存储和持久化混在一个服务文件里。

架构围绕一条运行主线：调用方请求历史数据，datalens 规划所需结构化数据集，检查持久化
覆盖范围，补齐缺失范围，持久化补齐结果，然后以流式响应返回。

## 端到端流程

标准流程是：

1. SDK/API 请求进入边界层。
2. 边界层验证请求格式和传输层约束。
3. 必要时兼容转换层把外部协议的表达转换成 datalens 原生表达。
4. 查询规划器构建可执行计划。
5. 存储层读取 Manifest 覆盖范围。
6. 规划器将范围分类为已覆盖、部分覆盖或缺失。
7. 存储层从对象存储读取已覆盖的数据分片。
8. 缺失范围解析器创建拉取任务。
9. 链适配器从链数据源拉取缺失范围。
10. 写入器标准化数据并持久化分片。
11. 持久化写入成功后更新 Manifest。
12. 响应组装层返回一个一致的结果流。

实现可以为了性能把这些操作流水线化，但可观察语义应保持一致。缺失数据在持久化写入之前
不能被标记为已覆盖。兼容格式不能泄漏到核心存储模型。

## Crate 和模块边界

`datalens-core` 保存共享词汇：链家族、链标识、范围、数据集、覆盖级别、标准化结果包和
通用错误类别。它不应该知道 EVM RPC 怎么工作，也不应该知道 S3 client 怎么配置。

`datalens-chain` 定义链适配器边界。它描述适配器能提供什么、能力如何报告，以及标准化后的
拉取结果如何回到链无关系统。

`datalens-evm` 是第一个链家族适配器。它拥有 EVM RPC/provider 集成、EVM 专属分页、
EVM 响应标准化和 EVM 错误解释。它不应该决定存储策略或原生 API 形态。

`datalens-storage` 拥有对象存储访问、Manifest 读写、持久化分片存在性检查和本地临时工作区
行为。它应该是唯一把对象存储当成持久化依据的边界。

`datalens-planner` 拥有查询规划。它将原生请求转换成可执行计划，验证范围和能力，决定所需
数据集，并结合 Manifest 覆盖范围找出缺失工作。

`datalens-writer` 拥有分片持久化。它接收标准化后的拉取数据，写入对象，验证写入完成，并以
安全顺序更新 Manifest 覆盖范围。

`datalens-api` 拥有边界层行为：HTTP 解析、原生 API 路由、认证接入点、响应流式返回和兼容
适配层。它在调用规划器前做边界转换，在原生响应组装后做兼容响应转换。

## 这一步先实现什么

第一阶段架构实现应该先创建 workspace 和 crate 边界，即使很多函数仍然只是骨架。这样后续
任务才有稳定位置加入存储、规划、EVM 拉取和 API。

第一批具体接口应该很小：

- `datalens-core` 中的链标识和范围类型。
- `datalens-core` 中的数据集和覆盖范围词汇。
- `datalens-chain` 中的适配器能力元数据。
- `datalens-storage` 中的存储 trait 形态。
- `datalens-planner` 中的规划器输入/输出骨架。
- `datalens-writer` 中的写入器输入/输出骨架。
- 一个能证明所有 crates 可以一起编译的最小 CLI 或服务入口。

## 为什么边界重要

如果 EVM 类型进入 `datalens-core`，以后增加 Tron 或 Solana 就会变成重写。如果 API 兼容
需求塑造存储，每一种外部协议都会制造一种新的缓存格式。如果本地磁盘变成覆盖范围依据，
对象存储就无法安全恢复或扩展归档。

这些边界让后续每个任务都可以更小：

- EVM 适配器任务可以修改 provider 行为，而不碰 Manifest。
- 存储任务可以修改对象存储后端，而不碰 EVM 逻辑。
- API 任务可以增加兼容能力，而不改变核心数据集。
- 规划器任务可以优化范围拆分，而不修改 HTTP 路由。

## 这一步的预期产出

系统架构阶段完成后，仓库应具备：

- crate 名称与架构一致的 Rust workspace。
- 核心边界的最小 public modules。
- 暂时不需要最终存储 schema。
- 暂时不需要网关兼容。
- 一个可编译的 baseline，供后续实现任务扩展。

这个阶段代码不需要真的拉取链数据。成功条件是系统形态正确，然后再逐步增加行为。
