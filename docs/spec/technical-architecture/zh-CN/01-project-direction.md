# 01 - 项目方向

这一步先定义 datalens 到底要做成什么，再让 crate、API、schema 或存储布局变成长期决策。

datalens 应该成为一个按查询驱动的结构化历史归档缓存，用来缓存区块链历史数据。EVM 是最早
实现目标，架构必须继续支持 Tron、Solana 和其他链家族。这个系统不只是某个已有网关协议的
兼容层。兼容可以有价值，但它必须建立在 datalens 自己的架构之上。

## 要解决的问题

索引器和数据应用会不断向链节点重复请求历史数据。对小众链或不被公共网关覆盖的链来说，
公共服务可能不可用、被限流、价格高，或者被其他产品假设限制。直接通过 RPC 索引仍然
可行，但每个项目都要重复处理历史读取、数据标准化、重试策略和存储。

datalens 要把这些重复的历史数据工作变成可复用能力。当调用方请求一段结构化历史数据时，
datalens 能从持久化缓存返回就直接返回；如果缺数据，就从配置好的链数据源拉取缺失范围，
标准化后写入持久化对象存储，更新覆盖范围元数据，然后返回请求结果。

## 产品形态

核心产品是一个服务，而不只是库。用户可以运行一个由对象存储支撑的持久化缓存服务。
应用、索引器和后续 SDK 都可以调用这个服务获取历史链数据。

服务应暴露原生 API，使用 datalens 自己的概念：链家族、链标识、数据集、范围、过滤条件、
字段选择、覆盖范围和响应流。SDK 可以让这个 API 更好用，但 SDK 不应该成为使用系统的
唯一方式。

开发者仍然可以选择完全从 RPC 直接索引。datalens 是为了改善重复历史访问，不是为了替代
每一个节点方法、内存池查询、待确认状态查询或低延迟运维 RPC 场景。

## 技术方向

持久化缓存应存储结构化数据集，而不是任意调用方响应内容。对 EVM 来说，这包括区块头、日志、
交易，以及必要时的回执。对其他链家族来说，数据集可能不同。共享架构不能强迫 Solana 或
Tron 数据进入 EVM 的日志主题或交易回执概念。

对象存储是持久化层。本地磁盘可以作为下载、上传、重试和查询执行的临时工作区，但不应成为
长期归档依据。

覆盖范围元数据和数据本身同样重要。因为 datalens 默认不会归档每一个可能的链字段，系统
必须能精确说明一个已存储分片覆盖了什么：链、数据集、范围、schema/标准化版本、过滤条件
和字段覆盖范围。

## 这一步的产出

项目方向阶段应产出：

- datalens 是结构化历史缓存服务的共同理解。
- EVM 优先，但不是唯一受支持链家族的明确决策。
- datalens 自有原生行为和兼容适配层的清晰分离。
- 对象存储优先的持久化姿态。
- 先稳定架构边界，再做网关兼容的开发顺序。

## 这一步不做什么

这一步不决定最终 Parquet schemas、最终 API endpoints、最终 object key formats 或最终 SDK
使用体验。这些决策要在架构边界清楚之后再做。

这一步也不要求完整全链归档。只存储调用方实际需要的结构化历史数据时，datalens 也应该能
产生价值。
